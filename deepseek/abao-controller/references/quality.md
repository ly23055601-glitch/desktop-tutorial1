# 全批统一去重与质检

输入是本次唯一的当前候选集、任务表、原帖证据、产品事实卡与父句记录。每条主评和回复有稳定定位 `task_id/comment_id`。质检不创建另一个创作任务，不在每个产品模块各自交付一份终稿。

## 1. 覆盖与数量

核对每个原输入位置及目标产品的去向；重复作品共享证据，但不同产品目标不自动合并。按用户实际要求检查主评/回复数，缺项与超额明确列出。用户没指定数量时采用共享写手默认值；不删除重复后偷偷少交，也不为补数写无关泛夸。

## 2. 全批去重

按三个层面依次比较：同一楼、同一帖、跨帖跨组跨产品。比较主评与主评、回复与回复，也比较主评和回复。短附和、准确术语和产品名正常重复不自动构成失败。

- **文本重复**：忽略空白、全半角、标点和英文大小写后相同的实质句子，先列为重复候选；按上下文决定保留、更换或说明重复理由。
- **意思重复**：只换人名、职业、地点、型号、表情或近义词，仍在说同一需求/同一结论/同一购买故事，视为需要审查的重复簇。
- **结构扎堆**：反复“背景＋使用场景＋卖点＋总结”、同样的开头、追问到解释再统一下单、所有末句同一收尾。依据整楼含义判断，不按字数、逗号数或术语词频扣分。

每簇保留最贴合原帖、依据充分且自然的一条，其他换真实关注点或重写互动关系；不是机械换词。相同术语但关注操作、使用条件、处理流程等不同意思可以保留，记清差异。修改后重新核对数量、父句、人物与事实，再比较整个最终集。

如需机器提示，可在具备 Python 且已下载仓库时执行仓库 `scripts/check_batch_quality.py`；它只提示文本完全重复、命名和结构问题，不证明语义不重复、事实真实或语言自然。没有运行则标注未运行，不编造报告。

## 3. 事实与原帖

逐句核对客观功能、参数、兼容、价格、模式、对比结论是否对应具体型号、条件和实际来源。`pending/conflict`、过期且未复核资料不得变成当前肯定事实。原帖设备未确认不能认作目标产品；未看的画面、未听的声音、未取得的作者回复不编造。

原帖事实、官方产品事实、编辑解释、公开人物原话、当批假想人物分别核对。角色的“用了多久”不证明产品功能；培训标签不豁免产品事实核验。已有真实稿审查不通过修改内容模式逃避问题。

## 4. 表达、回复和命名

先单独读每条主评是否成立产品兴趣，再读完整回复楼。父句能定位、指代清楚、说话者前后一致，不为预设答案反造问题，不代替博主承诺效果。声音和关注应自然有差异，无需固定短中长比例、职业配额、冲突或最后统一购买。

只对 Pocket 评论与回复检查 Osmo 禁用；其他品线不继承该禁词。型号、功能名准确，不靠错拼避重复。默认编号、单层四空格缩进和每条一行沿用共享规则；用户另有明确交付布局时按当次要求。

## 5. 定向修订与结果

问题表记录：定位、类别、具体问题、依据、处理、是否解决。类别为 `duplicate_text/duplicate_meaning/template_cluster/fact/model/evidence/reply/coverage/format`。不使用编造的“自然度百分比”或用总分掩盖事实硬错误。

- `pass`：最终版本的要求、覆盖、事实、回复和全批语义去重已检查，未解决硬问题为零；如脚本未运行，另列说明。
- `partial`：存在明确可用部分，但部分资料/任务/检查尚未完成；只交付可用部分及缺项。
- `blocked`：关键原帖、产品依据或用户要求无法支持交付；说明缺什么，不伪造通过。

任何正文修改后，旧的检查状态失效；重审受影响项并全批再去重。检查记录绑定最终 revision；有文件工具时保存实际最终稿 SHA256，没有则只用版本号，不能伪造哈希。脚本结构通过、语义审查完成与用户认可分别记录。

最终稿之外附简短摘要：原输入/唯一作品/任务数、交付/跳过、主评和回复实际数、去重改动数、未解决问题、语义审查与脚本执行状态。执行过程和内部人物标签不夹入评论正文。

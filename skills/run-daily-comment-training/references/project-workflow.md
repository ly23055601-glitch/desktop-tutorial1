# op 项目统一产出工作流

版本：`2026-09-15-WF-CW5.4.2`。本文件把项目约定、产品知识入口、统一采集、共享写手和每日台账串成一个可执行顺序。采集参数、产品事实和写作规则仍以各自当前技能为准，本文件不复制它们。

## 先判断任务类型

| 用户输入 | 进入路径 | 是否计每日新稿 |
| --- | --- | --- |
| 产品代码＋链接／材料，或“今日执行”“每日培训草稿” | 每日培训入口 | 是，除非全部是重发、改稿或验收 |
| 只读取链接、只分析帖子、审核已有稿 | 对应原入口 | 否 |
| 补充、纠正、验证产品知识 | 知识维护入口 | 否；按 `op → oq → ow → om → dm` 轮换，优先复用已有可核材料 |
| 明确核验真实消费者资料、本人亲历或旧稿 | 对应产品的真实材料／旧稿审查分支 | 否；保留原材料性质，不切换为训练稿 |

代码只决定产品线入口，不自行展开代际：`op` Pocket、`oq` Osmo 360、`ow` Osmo Nano、`om` Osmo Mobile、`dm` DJI Mic。产品代码和历史标签都不能证明原帖正在使用该产品。

## 每日新稿的固定顺序

### 0. 接单预检门（未通过的任务先登记为阻塞）

打开任何实时链接前，为每个输入建立预检记录：

| 字段 | 允许值／要求 |
| --- | --- |
| `product_code` | `op/oq/ow/om/dm`；未知或歧义代码不得猜测 |
| `product_line` | `pocket/osmo360/nano/osmo_mobile/mic`，由代码映射，不由标题推断 |
| `material_kind` | `social_url/user_provided_material` |
| `platform` | `douyin/xhs/bilibili/other/provided`；其他平台走全局 Chrome 规则 |
| `model_status` | `confirmed/unknown/not_needed`；记录原帖设备辨认状态。`unknown` 时不得把未核型号写成原帖拍摄设备，也不得据此断言硬能力。任务明确的目标型号或独立训练人物型号仍按当前写手规则使用，并注明其依据；它们不反证原片设备 |
| `evidence_need` | `metadata/visual/audio/dialogue/steps/comments`，按写作需要勾选 |
| `input_position` | 接收顺序的连续位置；保留用户原序号和重复项 |

同时标出跨产品同作品、已去重别名、同日重发／改稿和是否需要实时读取。预检未通过的单项仍留在 `inputs` 和对应 `G` 组，填具体阻塞原因；不能等采集后才发现产品路由错误。`B`／`G` 采用的规则、采集和知识版本在该组开始前冻结，组内不混用版本。

### 1. 规则和历史预检

读取两个来源任务的最近可读完成轮次，再以当前正式文件为准：

- 写手培训 → 项目写手入口 → 共享 `write-consumer-comments` 当前版本及按需参考
- 采集链接 → `read-social-links-with-social-helper` 当前版本及当次需要的 UI／问题交人工／证据参考

记录轮次、可读限制、技能版本和 SHA256 到 `runtime-sources.md`。读取最近 7 个实际执行日的终稿、明确反馈和必要诊断，历史助手评价、结构通过和未获用户认可的稿件不能升级为范文。规则在组边界变化时重新核对：已交组保留原版本，下一组采用新版本。

### 2. 登记输入和分组计划

先保存所有原序号、产品代码、原始 URL／材料身份、特殊要求和真实开始时间，再做去重映射。一次请求是一个 `B` 批次；任务是“产品代码＋原帖／材料”；同作品跨产品拆任务、共享采集证据。统一采集按作品去重，但输入位置、别名、重复和失败不能删除。

输出组 `G` 只按输入数组位置切分：`1–10、11–20…`，尾组照常保留，不按产品线或平台重排。采集平台批次和 10 条输出组是两套边界；不要为了凑满输出组重采或把后组输入提前。

### 3. 统一采集和证据交接

全部渠道先登记完整集合；抖音、小红书、B站链接一次性交给统一采集技能，首次所需内容层由它统一规划，同一浏览器侧栏只允许一个活跃控制者。其他平台按全局规则批量组织，用已连接外部 Chrome 单次读取原页可见内容。取得结果后，逐作品接收并进行一次离线证据验收，使用下列最小 evidence pack，字段名固定，方便写作、台账和复核消费：

```json
{
  "work_id": "douyin:123",
  "input_orders": ["1", "7"],
  "source_input_orders": ["1", "7"],
  "alias_refs": ["douyin:短链"],
  "summary_basis": ["caption", "visual", "audio", "transcript", "comments"],
  "anchors": [{"field": "visual", "ref": "evidence/visual-01.png", "sha256": "…"}],
  "comments_status": "read/not_requested/unavailable",
  "media_paths": [],
  "read_method": "social_helper/user_provided/chrome",
  "attempts": [],
  "retrieved_at": "带时区 ISO 时间",
  "confidence": "qualified/limited/blocked",
  "limitations": []
}
```

已取得的下载或转写文件复制到批次的 `evidence/` 目录并记录 SHA256；Chrome Downloads 只是暂存位置，不能作为长期 `evidence_ref`。`attempts` 只镜像实际首采与人工交接记录，问题处理只按统一采集技能的交人工规则，不追加下载重试、修链、换模式或原页复查。`qualified/reused/provided/blocked/pending` 的 KPI 状态与原始采集状态并存，不能互相覆盖。证据包和文件落盘后才允许将任务门标为 `evidence_ready`。

导出成功或进度完成不等于证据合格：标题／正文只能支持已读字段；画面、声音、对白、笑点、教程步骤和完整叙事必须有对应媒体或转写。证据不足时汇总“作品 ID＋缺失证据＋判断用途”交人工，保留原序号和已有材料；写作者不得以补读让失败作品重新入队。`Debugger unattached`、验证码、登录、面板被占用和队列归属不明时同样依统一问题交人工参考处理，保留已知提交状态和尝试历史，不把控制故障改成作品失败。人工另交材料可按统一规则验收。

采集失败不等于整批失败：成功作品继续写作，失败／pending／blocked 保留在原输入位置和任务分母。结构化证据不足但用户另给充分材料时，登记 `provided` 替代来源，保留原读取失败。

### 4. 按产品入口取知识

每条任务只读取当前需要的少量知识，不把整库塞入正文：

| 代码 | 内部 `product_line` | 先读产品入口 | 按需追加 |
| --- | --- | --- |
| `op` | `pocket` | Pocket 个人入口及 Pocket 写作边界 | 卖点、详细场景、观感／审美、使用习惯与原句反馈 |
| `oq` | `osmo360` | 项目 Osmo 360 入口 | 两代事实、卖点、场景卡、空间视角／拍后选择体验 |
| `ow` | `nano` | Nano 能力入口 | 卖点／场景、佩戴／第一视角体验、真实原句、人群假设 |
| `om` | `osmo_mobile` | Mobile 个人入口 | 兼容与场景、拍法／真实表达、角色心理 |
| `dm` | `mic` | Mic 个人入口 | 连接与录音事实、场景、佩戴／声音体验和真实讨论 |

每个任务另存 `knowledge_handoff`：`product_line`、`model_status`、选用的事实／场景／体验材料 ID、来源路径、核验时间、`pending`／`conflict`／不适用项，以及 `knowledge_version` 和 SHA256。型号未确认时，handoff 可以继续支持非型号化表达，但不能进入型号或能力硬断言。跨产品共享同一作品证据时，handoff 必须分别绑定产品事实，禁止把一条产品线的知识复制到另一条。

产品事实保留型号、条件、来源和核验日期；`pending`／`conflict` 不能写成肯定能力。卖点是编辑解释，场景和心理是待验证假设，体验语料保留原话、原帖、父句和阅读范围；真实材料、假想人物和原帖证据永远分开。知识补充按 `op → oq → ow → om → dm` 轮换，但知识维护不抢占每日采集，也不计每日新稿。

项目写手入口是每日默认路由；用户明确调用个人写作技能时可以从个人入口开始，但评论最终仍只进入一次共享 `write-consumer-comments`。个人入口已完成的知识读取不得被项目路由重复加载；Mic 等“直接取资料”措辞只表示防止循环回调，不表示跳过共享写手。共享体验材料索引统一参考 `/Users/luocaihua/.codex/skills/write-consumer-comments/references/experience-materials.md`，产品自己的体验文件按需追加；文件存在、字幕存在或转写完成不自动等于已听／已看，handoff 要记录实际阅读范围。

### 5. 识别任务语境，再选择写法

进入共享写手 `2026-09-15-CW5.4.2`：先判断整帖在展示、分享、教学、比较、求助还是表达态度，产品是讨论对象、已确认工具还是消费者联想对象，再从知识中取一两个相关关注点。

达人主页与未发布新品预写按共享[学习经验](/Users/luocaihua/.codex/skills/write-consumer-comments/references/calibration-20260915/learning.md)使用已取得往期材料及任务产品目标；不把拟发布内容写成已见，不按昵称或分类猜风格。当次数量与单元格布局按明确要求执行，仍分别计主评、回复，不把480条等历史批次数量设成默认

- 产品语境清楚且效果已展示时，直接喜欢画质、色彩、气色、质感或声音可以独立成立，不强加型号、经历、追问或购买结论
- 由整帖引起的相关场景期待、假想使用感受和偏爱可以成立，不要求原帖地点、人物和动作相同；设备未确认时不得写成目标产品拍摄事实
- 只有确有信息需要时才问参数、原片、补拍或教程，不把追问博主当默认互动
- 若原帖确有两台及以上设备同场景实拍、成片对照、可核验排名或使用后取舍，进入当前横测分支：先核对参与产品、比较轴、结论和证据强度，再以任务指定产品为种草中心，至少一条主评明确点名目标品牌或型号；普通“哪个好”求助没有对照证据时不触发横测

### 6. 写作和组内复核

仅当 `evidence_ready`、`knowledge_handoff` 完成且整帖理解记录存在时，任务才进入 `ready_to_write`。每个任务的最小选材记录包含：整帖类型／产品角色、选用产品事实 ID、消费者关注点、人物设定（如有）、横测触发与证据、主评角度和拟展开楼。人物是培训虚构，不写入产品事实或用户反馈。

每帖通常 3–4 条主评；确实只有两个独立成立角度时可减为 2 条并说明。每帖选择 1–2 条主评各展开 5–8 条产品讨论，其余主评 0–4 条回复。短问、调侃和短附和可以留，但不能靠连续认同、重复解释、轮讲卖点、共同设计方案或统一下单凑数。

主评先独立成立，再展开楼中楼。主评逐条检查产品兴趣；回复逐条核对直接父句、声音、人物、产品／原帖事实，讨论价值看整楼。自然长句可以保留，短句说清可以停止；不设字数、长短比例、标点或分类得分。

先并排读同一帖的主评和回复，再与同组、前组及最近 7 个执行日稿件比较真正想说的事、语气、开口、解释、结尾和互动走向。重复时先换消费者真正想说的事，不只替换产品名、职业、地点或称呼。

术语重复与表达扎堆的判断，读取共享[句义与术语详略](/Users/luocaihua/.codex/skills/write-consumer-comments/references/writing-reference.md#同一卖点按句义选择详略)（2026-09-15修订）；保留已成立原句，逐句决定条件是否需写出，不用整批统一删、加或替换完成去重。本入口不另设词频或写法比例

### 7. 结构检查、留档、质检和交付

新稿显式运行：

```bash
python3 "<共享写手技能目录>/scripts/check_training_comments.py" training-state.json --profile cw5 --json
```

机器只检查 2–4 主评、每楼最多 8 回复、至少一楼达到 5 回复等结构；横测比较轴、两主评减量理由、通常 1–2 组展开楼及语义质量仍由内容审稿判断。最终保存正文、证据、训练 state、SHA256、检查报告和语义记录；组文件顶部只标一次“培训用假想消费者草稿”，编号主评，回复单层四空格缩进，教学说明另存。每批另存 `delivery-manifest.json`（字段参照[manifest 模板](../assets/delivery-manifest.template.json)），逐输入列出 `task_ref`、`draft_ref`、`training_state_ref`、`evidence_ref`、`review_ref`、采用规则／知识版本、SHA256、限制和当前状态；交付前执行 `inputs → evidence → task → draft/state/review → G` 覆盖校验并把差异清单放入 manifest。

在上述结构检查后运行独立 `training_cw5` 质检。全量任务至少完成 L0 证据门、L1 结构门和基础评分；新写手、横测、敏感型号、历史高风险稿及随机样本追加独立深度复审。质检输出 `quality-review.json` 与 `quality-review.md`，绑定当前正文 SHA256，记录维度分数、硬错误封顶、问题码、证据、改写动作和复检状态。质检分数不能替代原有 `review` 矩阵，深度抽样结果不能表述为整批语义通过。

交付可见文件与内部文件分开：可见层是组稿和简短统计；内部层至少含 evidence pack、knowledge handoff、训练 state、机器检查、语义审查、`quality-review`、runtime-sources 和 manifest。任何一项缺失都标为受限或未完成，不以“脚本通过”代替。

实交、教学完整、助手自检、独立审稿和用户验收分别记录。材料不足或讨论不足可交成立部分和缺口，但不能计教学完整；用户没有明确反馈记待验收。改稿更新原任务和版本，不新增产量；同日新增材料另建批次。

## 收尾信息

每组报告原输入范围、实交／教学完整／受限数量；每日收尾报告输入与完成、主评／回复／长讨论组、采集阻塞、证据缺口、自检问题、用户验收、耗时和返工。KPI 脚本的 `draft_completion` 仅代表实交，不代表当前写手教学完整；前 7 个实际执行日先记录，不提前设验收率或分钟门槛。

## 反馈与知识维护边界

收到修改或认可后先做反馈分流：`single_task/same_group/product_line/shared_writer/collector`，保存用户原话、目标任务／版本、时间、是否授权升级（`authorized_to_promote`）及影响的规则版本。单帖偏好不得自动写回共享写手；获得明确授权后才更新共享反馈或产品知识，并在下一组冻结点生效。修订后同步刷新对应 G 组、manifest、state、review 和 SHA256，首稿快照保持不变。

知识维护继续按 `op → oq → ow → om → dm` 轮换，和交付路由顺序分开记录。每次维护追加统一 change ledger：`add/correct/verify/pending`、来源、`verified_at`、旧／新快照 SHA256、受影响事实／场景／训练版本、下一步；维护后跑入口 smoke test、引用完整性检查和产品审计，再更新轮换状态。价格、固件、兼容等时变事实写复核日期，不计入每日新稿 KPI，也不创建定时任务。

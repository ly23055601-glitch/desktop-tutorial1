# 每日培训草稿执行

本入口只维护每日调用、留档和计量。先读取[项目级统一产出工作流](references/project-workflow.md)，再按其中顺序执行。产品映射使用[项目约定](../../../AGENTS.md)，采集使用[统一社媒读取技能](/Users/luocaihua/.codex/skills/read-social-links-with-social-helper/MODULE.md)，写法使用[项目写手入口](../write-consumer-training-comments/MODULE.md)及其共享技能当前文件；不复制采集参数、旧审核评分或产品规则。

产出顺序：核对当前规则与近期反馈 → 登记完整输入 → 统一采集并核对证据范围 → 按整帖选择消费者关注和产品知识（识别当前横测分支）→ 每 10 个输入位置写作、同帖及跨帖复核 → 运行 `training_cw5` 质检 → 交付 → 更新台账与反馈。采集完成、材料足够写作、教学完整交付、质检状态和用户认可分别判断。

## training_cw5 质检

质检使用项目内独立实现的 `quality-review` 工具和 `training_cw5` profile。所有任务完成证据、结构、事实绑定和基础评分；新写手、横测、敏感型号、历史高风险稿及随机样本追加独立深度复审。质检文件绑定当前稿件 SHA256，保留首稿与修订版本，不能把结构检查通过当作语义质检通过。硬错误触发封顶或阻塞，百分制只用于无硬错误时的质量分级。详见[台账契约](references/ledger-contract.md)与质检工具目录。

批次和写手画像由只读汇总器生成，不改写每日 KPI 台账：

```sh
python3 .agents/skills/run-daily-comment-training/scripts/quality_summary.py \
  outputs/quality-review-pilot --pretty \
  --output outputs/quality-review-pilot/quality-summary.json
```

## 启动与承接

用户在 op 项目提供已映射产品代码与链接／材料，即可开始；“今日执行”是可选启动词。当次明确要求、数量及输出格式优先。只询问无法从输入与项目资料确定且影响结果的信息，不重复确认已有默认值。没有任务材料时不建立空批次。

```text
今日执行
op
1. 链接
2. 链接
dm
3. 链接
当日特殊要求：有则填写
```

首次使用本入口读取[台账与 KPI 契约](references/ledger-contract.md)。正式数据根目录为本项目 `outputs/daily-comment-training/`；工具与试验不使用正式日期目录。首次真实接单才创建 `YYYY-MM-DD/B001/`，日期以 `Asia/Shanghai` 为准。

启动时运行只读汇总工具定位最近 7 个实际执行日和本日批次。读取其最终稿、反馈记录与必要诊断，结合当前输入检查重复；材料多时先按产品／主题检索，再复核跨产品的相同表达机制。认可范围以用户原话为准，历史稿、助手评价与结构通过记录不当作认可范文。

```sh
python3 .agents/skills/run-daily-comment-training/scripts/daily_kpi.py outputs/daily-comment-training --json
```

命令在 op 项目根目录运行。旧稿续接依据文件，不要求重读历史执行对话；上文两个规则来源任务的每日版本核对仍照常执行。确需定位未落盘的用户反馈或无法确定旧批次时，再读取相关执行任务或澄清具体对象。

## 每 10 个链接一组工作与输出

区分接单批次 `B`、统一技能管理的采集批次和输出组 `G`。一个 `B` 保存本次请求的完整输入；统一采集可以多于 10 个；`G001/G002/…` 只负责按 10 个链接推进选材、写作、复核和交付，不成为拆采集的理由。

- 按 `ledger.inputs` 的原到达顺序，每 10 个输入位置一组，不按产品或平台重排。例如 23 个输入为 `G001:1–10`、`G002:11–20`、`G003:21–23`，不足 10 个不等补满；0 个不建组。使用者原序号原样保留，另以连续输入位置确定边界，避免用户重复编号影响分组。
- 每条输入携带其 `op/ow/om/dm/oq` 产品线；跨产品同作品仍各自取知识、表达和复核，采集证据可共用。重复或失败条目保留组内位置：重复条目引用对应任务和已有稿，失败／待处理条目说明实际状态，不重写凑量、不虚报完成，也不把后组条目提前补入本组。
- 全部待读取链接先登记完整集合，三平台链接一次交统一技能，其他平台按全局 Chrome 规则批量组织；消费返回证据后按组推进。先完成当前组的选材、主评与回复、内容复核和交付，再继续下一组；可在采集下一平台批次时处理已完整取得证据的组，但不另开并发采集。组间继续检查关注点与句式重复，不能每 10 个就清空全批次差异检查。
- 无需用户逐组说“继续”。每组给出独立交付文件与简短进度，直到本次全部组都有实际稿件或明确状态；遇登录／验证码等问题依统一技能及全局规则保留原序号交人工，继续处理可用材料，不把未完成组改记成功。输出组有受限项仍按原序号列出，组的说明不替代稿件完成指标。
- 后续新链接请求另建 `B`，重新从 `G001` 按 10 分组，不把后来链接塞进已交付尾组。纯改稿／验收不增加输入位置和输出组，只更新原任务及其对应组的交付引用，保留首交记录。

每组对外保存为接单目录下的 `G001.md` 等文件，并在对话中依次提供该组内容或文件链接、原编号范围和实交／教学完整／受限数量。组文件顶部只标一次“培训用假想消费者草稿”，逐项显示原序号、产品线和材料定位，每帖从 1 编号；按共享当前格式，每条评论正文一行，回复单层四空格缩进，不显示人物 A/B 标签或创作说明。同一帖的主评和回复不得跨组拆开。每任务独立稿件和训练 state 继续保留；组文件汇编实际任务终稿及重复／失败说明，不把多个任务强塞进一个共享 state。改稿先更新任务终稿，再刷新相应组文件，交付前按分组清单核对恰好覆盖全部输入位置及正确任务版本。

## 执行一批任务

1. **登记完整输入。** 记录真实开始时间、当日要求、产品代码和全部原序号；任务单位为“产品代码＋原帖／材料”。代码不自行展开为具体代际。依统一读取返回的作品 ID 合并短链别名；已知重复保留输入映射，同一链接跨产品复用证据但保留各自写作单位。无法匹配的代码或材料保留阻塞，不静默丢弃。
2. **统一取得证据并判断能读到什么。** 需要实时读取时，先完整遵循统一社媒技能，将本次请求全部抖音、小红书、B站链接一次交入，不按产品、输出组、写作分工或单帖审稿拆采集。其他平台同样登记完整集合、按平台批量组织，依全局规则用已连接外部 Chrome 单次读取原页可见内容；充分用户材料可直接使用。首次所需画面、声音、对白、教程、叙事或评论层由统一流程预先规划，不默认采集真实评论／楼中楼来生成假想回复。消费逐作品证据包并进行一次离线证据验收，沿用作品 ID、sourceInputOrders 与脱敏别名映射，核对 summaryBasis、锚点、评论状态和缺口；下载文件存在不等于已经看懂内容，任务完成提示不等于证据合格。标题／正文只能支持已读字段。证据充分才进入依赖它的写作；不足时汇总“作品 ID＋缺少的证据＋判断用途”，按统一技能的问题交人工规则保留原序号和已有证据，其他任务继续，已失败作品不以补读重新入队。浏览器控制中断、队列归属不明等问题同样交人工，保留已知提交状态和尝试历史，不把控制错误写成平台拒绝，不自动复查原页或自修控制后重采；用户另交材料可按统一规则验收，其他写作者只消费已取得的材料。
3. **先读懂整帖，再取相关知识。** 从项目写手接入共享当前技能，阅读表达参考和压缩反馈；需要辨别细类时再读[帖子类型与产品话题](/Users/luocaihua/.codex/skills/write-consumer-comments/references/post-type-selection.md)。简记整帖在讲什么、产品角色、主要吸引力和最顺的表达方向，按每条产品代码进入知识库，按精确型号、实际活动和消费者关注取产品事实、卖点与使用价值、详细场景，必要时取角色心理假设。不先编人物故事再找原帖细节过渡，不把类别固定绑定功能，也不把整库机械塞进评论。任务产品标签不证明原片设备；知识入口及未变化参考不循环加载，产品型号、条件和引用核验仍由对应知识规则负责。原帖证据、产品事实、培训人物分开，未知事实不借假想亲测补齐。
4. **选择自然表达，主评成立后再展开。** 当前 CW5.4.2 允许产品语境明确且已展示相关效果时直接表达喜欢，不强加型号、使用故事、追问或购买结论；由整帖引起的相关场景期待、假想使用感受和偏爱也可成立，不要求原帖出现同一地点、人物和动作。若原帖有两台及以上设备的实际对照、同场景实拍比较、可核验排名，或使用后明确取舍，先进入共享横测分支：核对对照对象、场景、排名或取舍的证据范围，分别核验各产品事实与条件，再以任务指定产品为种草中心，至少一条主评明确点名目标品牌或型号，竞品只作必要参照，不写成等量推荐。只有单纯求助、咨询或想了解差异而没有实际对照证据时，不误判为横测，也不补造对照、排名或使用后结论。每条主评分别成立产品兴趣，无关泛夸或重复赞叹不能占位。不默认向博主索要参数、原片、补拍或教程，有实际信息需要才问，有更新线索才等后续。保留有作用的长句，短句说清即可停，不安排固定人物、心理分析结构或短中长顺序。主评独立成立后选适合的楼展开，讨论价值看整楼，短问、调侃、普通附和可保留，不要求每人新增卖点，不预设完整问答或下单结尾。数量与接口始终服从共享当前文件；现行仍为通常 3–4 主评、仅两个成立角度时减为 2 条并说明，每帖 1–2 组各 5–8 回复、其余 0–4，新稿显式使用 `--profile cw5`。不足先从已有材料重新选材，缺证按统一问题交人工规则处理；仍不足标教学未完成，不用凑数补质量。
5. **先同帖、再跨帖复核正文。** 先看原帖与正文，再看创作解释。逐链接并排读各主评，再读该帖全部回复，比较消费者关注、熟悉度、态度、语气和篇幅；主评逐条检查贴合整帖和产品兴趣；回复逐条检查声音、人物、直接父句及产品／原帖事实，产品讨论价值看整楼，长讨论读到最后一条。横测分支另核对照对象、同场景条件、排名依据和使用后取舍是否均有原帖证据，避免把普通求助写成比较结论；每个产品的事实、型号和条件分开复核，表达与互动保持共享规则。然后与本组其他帖、本批前组和近期相关稿比较开口、句式、解释、结尾与互动走向；不能用别帖长短范围掩盖本帖同一种声音，也不能只换身份或称呼算差异。长度仅作定位线索，不设字数、长短比例、逗号门槛或机器自然度分。保留好句，重复时先换其他消费者真正想说的事，不统一删尾、全改短句或连续“蹲”；减少反复背景＋用途＋价值总结、无用三连列举和为答案铺垫。问题定位到原句，修改后重新核对事实、表达与完整交付要求。可用子代理时交给独立审稿者，同帖主评与回复一起复核并共用已有证据；只能自审时记录未做独立审稿，不另开采集。结论沿用既有审稿记录，不新增评分或 state 字段。
6. **留档、按组交付并继续。** 按共享[训练契约](/Users/luocaihua/.codex/skills/write-consumer-comments/references/training-contract.md)保存最终编号稿、证据、训练 state、正文 SHA256 及实际结构检查报告；内容判断、选材取舍和教学说明另存。每任务单独保存草稿与 state，使用真实原帖／材料 ID；跨产品同作品可共用证据，不合并到一个含重复 ID 的 state，也不伪造 ID。按本节上方的组格式汇编并核对全部原输入位置、当前版本和状态；有成立部分但尚不完整时明确标示，不能记教学完整。每组交付后自动继续下一组，最后汇总实交、教学完整与用户待验收状态，三者不互相替代。

每次新链接／材料请求是新接单批次，完整 `inputs` 留在新批次供分组，`tasks` 只定义尚未登记的新单位；重发条目的 `task_ref` 指向原任务，不创建新增产量。全是重发的新链接请求可有 `inputs` 而没有新 `tasks`，仍返回引用组但不新增执行日。创建目录时取当日未使用的下一个 `B001` 式编号，用不可覆盖的目录创建确认占用；撞号读取最新目录后另取编号。只有修改或反馈时继续更新原批次，不创建新批次。

登记实交时须保留该任务实际可用的原帖／材料来源；只有读取失败或待处理记录、又无替代材料时不能记 `delivered`。读链失败后采用用户另给的充分材料，应在台账另登记该材料的 `provided` 来源，保留原读取失败，不能为了通过检查把失败改成读取成功。

改稿与验收始终更新原任务所属批次，跨日修改不新建产量或执行日。同一产品、同一材料在同日的新训练方案也归入原任务，以版本保存，不增加任务数；新日明确发起新的训练任务时可建立当天任务并记录要求。普通重发、换文件名或对旧稿继续修订不当作新任务。修订保留首交快照和反馈事件，当前稿由台账指向最新版本，不把新旧正文混写进一个编号稿。修改正文后重新生成对应 state 绑定与检查。

## KPI 与反馈

使用[台账模板](assets/batch-ledger.template.json)登记实际事实，已有机器字段与公式以台账契约为准；模板不能原样作为正式记录。每批同时读取[最新 KPI 口径](references/kpi-standard.md)，按实际写手版本记录教学完整交付。KPI 独立于共享训练 state，不向共享检查器添加评分字段。汇总工具只核对计量结构和计算，不能证明证据真实、表达自然或用户已认可。

- 每批报告输入闭环、去重读取成功、稿件实交、教学完整交付、硬错误、内容复核覆盖、首稿验收及审阅覆盖、真实耗时和用户反馈后的修改轮次。脚本 `draft_completion` 仅表示实交；教学完整须结合实际正文、检查配置和语义审查另记完整／未完成／未核，不能从复核标记推定通过。闭环、复核覆盖目标 100%，硬错误目标 0；没有分母记“暂无数据”。受限材料保留在任务分母里，不能以排除难题提高完成率。
- 助手自检、独立审稿、用户验收分别登记。自检通过不等于用户认可；没有明确反馈记待验收，不算失败也不算通过。反馈只覆盖明确提及的帖子／版本，整批明确认可才覆盖整批；无法确定对象的笼统评价暂存批次备注，不猜逐帖结论。
- “第 1 帖可以，第 2 帖改口吻”只给第 1 帖首稿认可，第 2 帖记录修改要求；随后第 2 帖新版获认可，只更新当前版本验收，不能将首稿回写为通过。发现已交付硬错误，修复后仍保留问题及其发现、修复记录；培训人物经历本身不计作硬错误。
- 当日局部偏好只在其范围内承接；明确适用于共用写法的纠偏，在获授权更新中回到共享写手的反馈来源维护。不因每日留档自动修改共享规则或产品知识。

当日交付或修改完成后再次运行工具，针对指定日期可加 `--date YYYY-MM-DD`。把结果另存批次或当日日报，并按 KPI 口径补充教学完整交付状态，不能把解释性统计夹入培训评论正文。给用户的收尾压缩为：输入／实交／教学完整、主评／回复／长讨论组、阻塞、自检问题、用户验收、耗时／返工；提供草稿与日报文件链接，用户未要求解释时不展开内部审稿。

## 七日基线

前 7 个**有真实新任务的上海日期**为基线执行日，跳过无任务日；只有修改、反馈或测试的日期不计入。各日多批次合并计量，保留任务分母与未验收状态。没有满 7 日时显示已积累几日，不补造历史数据或套用审核表 85 分门槛。

第 7 个执行日收尾时，依据工具汇总的首 7 日台账，记录首稿验收率及审阅覆盖、各类问题、批次耗时／外部阻塞和返工分布，提出下一阶段目标建议。未被用户明确采用前不设新的验收率或分钟目标；若反馈稀少，说明样本不足。当天还有新批次或后续补验收时可更新同一基线报告，注明汇总时刻。

本入口不创建定时任务、不发布评论、不操作账号。已有稿表格审核、专项真实材料核验、只读分析及知识库维护继续走原入口，不混入每日新稿产量。

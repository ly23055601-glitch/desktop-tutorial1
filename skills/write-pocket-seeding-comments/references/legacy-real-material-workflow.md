# Pocket种草评论｜op项目版

保留版本：`2026-09-05-LH13`。本页仅供[现行CW2入口](../SKILL.md)指定的真实材料专项核验或旧稿复核；以下是该模式的原规则、模板和检查器，不是普通CW2训练写作入口

目标是让观看者因为原帖，对Pocket产生具体兴趣：一种想尝试的用途、想了解的操作、产品细节带来的喜欢，或真实需求被内容接住。热评学习用于增强表达自然度。每帖须有清晰的Pocket兴趣，单纯出现型号或把全帖写成夸人夸景，不算完成种草

本技能只产出草稿与验收结果，不发布、不代写已经发生的消费者互动，不代表每条都是用户已认可的固定话术

## 从材料开始

1. 有新抖音、小红书、B站链接需要读取时，先完整遵循 [统一社媒读取技能](/Users/luocaihua/.codex/skills/read-social-links-with-social-helper/SKILL.md)，一次交入本次全部链接并保留原序号。本技能不另定采集、重试或停止方式
2. 已有充分用户材料或社媒助手证据时直接使用，保留来源。只看过抽样帧不能补写对白、音效、连续动作或完整教程结论；标题与标签也不能写成视频前后说过的话
3. 读帖先找值得回应的动作、情绪、原话或画面，再判断它如何让人对Pocket感兴趣。产品型号和具体功能分别确认，未确认代际时用Pocket、大疆Pocket等称呼
4. 初次使用本项目标准，读取 [写作与案例](../references/writing-and-examples.md)和 [本人素材](../references/project-context.md)。涉及产品能力、外观细节、参数或价格时，再读取 [产品事实](../references/product-facts.md)，核对当前官方资料

### 按当前帖调用知识库

读取 [Pocket知识库索引](../../../../knowledge/pocket/INDEX.md)，在确认当前帖的型号、场景与开口理由后，用具体中文问题检索少量产品知识、场景过程、表达和接话材料：

```bash
python3 knowledge/pocket/scripts/pocket_knowledge.py search '独自旅行 怎么把自己拍进去 跟随' --model pocket_4 --platform xiaohongshu
```

型号不明时省略`--model`，平台按当前帖填写；从结果中选择与原帖有关的内容形成内部参考，不把输出各类固定变成评论槽位。引用保留事实ID、语料ID和来源定位。`pending`只作为待核缺口，`case`只作个案，`editorial_hypothesis`不能当作已观察的人群规律；第三方经历用于理解处境，不转成当前评论角色的过去经历

默认不读取holdout，只有对照验收阶段可显式包含。知识卡和历史语料都不是当前帖证据，不能提升原片型号/功能等级；知识事实也不会自动登记为claim。正文实际使用产品断言时，重读当前官方页面，已有claim按`product_facts`绑定原句，未登记项先核验、补注册和必要回归。检索没结果保留缺口，不猜测补齐

原片没有Pocket身份也可产生“我想带Pocket尝试”的联想，不能反过来说原片由Pocket拍摄。连两个独立表达都撑不住，或找不到成立的Pocket兴趣时，补证、减去该帖或说明不足，不用泛夸和假经历补齐

## 先有开口理由，再决定数量

- 每帖2–4条主评，每条0–4条回复。两个好角度就写两条；需要一句就接一句，说够便停，不为展示各种数量凑满
- 同帖可以共同种草，但具体心动理由或想解决的问题要有区别，例如配件拥有欲与操作偏好，自拍可行性与旅行记录期待。不能换三处画面仍重复同一个“我也想拍”；也不能因为都表达想拍就删掉其中所有产品意图
- 主评中可有纯画面感受、短反应和接梗。锚点留在内部，不要求每条重述画面。不固定两条点名加一条无名，无名评论也不固定最后一条
- 产品应参与句子在说的事，不能把型号贴在衣服、布景链接或通用夸赞前面。参数只写与当前兴趣有关的一点，避免把说明书缩成评论
- 当前的喜欢、好奇、犹豫和使用念头可以写；过去的持有、购买、实测和具体使用感受须有真实材料。只在本人备选稿中采用已确认的本人素材，不把同一份经历分给多个评论角色
- 情绪从内容里来，不给每条统一加“救命、谁懂、哈哈、心动”或表情。删去第二遍解释、假装周全的取舍和总结，避免主动与博主较真、劝退换机

## 楼中楼顺着前一句

内部记录说话者和直接父句，对外只给编号主评和缩进回复

- 第一条回复接主评正在说的情绪、问题或愿望，后续跟着新出现的内容走，不统一安排ABA或ABC
- 主评已说过的事情不重新设问；不要“复述主评→确认复述”，也不要总是“教怎么拍→接受建议”
- 接玩笑、补一个当前偏好、回应顾虑都可以。没有下一句值得说，就零回复，不把俏皮旁白当作对话
- 不代编博主回答，不虚构角色间的熟人关系。本人材料不能被另一位回复者继承
- 无名主评的回复无需补产品名；回复一旦谈到产品能力，仍逐句核验，不能借其他组的型号和证据自动通过

## 统一格式

- 评论正文不用Osmo，包括大小写变体；来源文件和官方名称不受此限制
- 产品英文名与型号内部连写，如Pocket4P、4p、Pocket4、p4；同帖实际点名的称呼适当变化，不能为了换称呼改型号或硬造简称
- 主评及回复正文不使用中文句号、句末英文句点；编号中的点、小数和有效链接中的点不算正文句号
- 长短、问号、感叹号、逗号和表情随表达变化，不设配额

```text
## 原序号｜原帖链接

1. 按当前内容成立的一条主评论

    - 有自然回应才写
```

每帖主评从1连续编号，回复用单层缩进项目符号。示意只有一组，不表示交付只写一组。正文只维护这份编号稿，类型、证据和角色不另做一套供交付的文案

## 验收与状态

实际批次使用 [LH13状态模板](../assets/pocket_comment_state.lh13.template.json)。状态、事实和审稿接口见 [检查契约](../references/checker-contract.md)，机器可复核格式、声明与已登记事实，不能判断所有语言含义

每组记录真实主锚点、`dominant_expression`、相关时的`product_connection`及实际说话者/父句。每帖同时并排审稿，并在`qa.semantic_review.seeding_review`记录哪条正文带来什么Pocket兴趣，引用最终原句。用最终稿SHA256绑定审稿，不能沿用旧稿passed

纯观察、愿望与疑问不强制升级成强卖点。LH13的独立官网事实用`product_facts`逐句绑定，事实成立不等于原片效果由它造成，也不能提高原帖的型号或演示等级。新增事实没有登记时先核验、补登记和必要回归，不冒用旧claim或通过删掉产品意图追求全绿

```bash
python3 .agents/skills/write-pocket-seeding-comments/scripts/check_comment_homogeneity.py draft.md --state state.json --product-policy off --seeding-policy strict --format json
```

交付前逐帖读出：回应原帖什么；读者会对Pocket多出什么兴趣；各条在想不同的什么事；回复是否接住父句；产品与个人事实是否有依据。整批再听句式、笑点、顾虑和对话走向，不能只比较词语相似度。风格警告逐项审读，不通过删逗号或强行改长度消警告

四帖以上或用户要求验收时，使用独立审稿；审稿者读取原材料与当前正文，不把上次结论当成本次通过依据。脚本报错和语义退回分别处理，最后保存逐帖结论与实际检查结果

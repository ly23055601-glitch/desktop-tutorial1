# 来源与版本维护

## 内容的维护入口

`products/*.facts.jsonl` 是事实的维护入口，按型号拆分。`sources/*.jsonl` 是来源登记。模块、产品档案、FAQ 和题目引用知识卡编号；`CARDS.md` 和 `sources/INDEX.md` 由脚本生成，不直接编辑。

每条知识卡字段：`id`、`kind`、`models`、`topic`、`statement`、`conditions`、`limitations`、`region`、`firmware`、`software`、`sources`、`checked_at`、`status`。来源引用包含 `source_id` 和 `locator`；定位使用页面小节、表格型号列或 PDF 印刷页码，并注明 PDF 页序与印刷页码差异。

`firmware`、`software` 为 `null` 时表示本卡没有记录专属版本条件，不表示所有版本都支持。需要明确版本的能力必须补齐；官方没有给出版本时写入边界，不自行猜测。

来源记录包含标题、实际读取 URL、发布方、语言、地区、适用型号、核验日期、读取状态、定位和读取范围说明。发布日期或文件版本可写入说明；页面未注明时记录“未标发布日期”，不拿访问日替代发布日期。

## 更新步骤

1. 阅读实际官方页面；从集合表逐列确认型号，核对正文和脚注。旧记录可作线索，不作为本次已读取证据。
2. 在来源清单登记读取范围和日期。失效链接记为未读取；为替代链接新建来源编号，保留原记录。
3. 修改受影响卡片，保留适用模式、地区和版本。卡片表达同一问题的新版本时沿用 ID；不同功能或不同适用条件需要独立卡片。
4. 搜索该 ID 的全部引用，同步更新档案、课程、比较、FAQ 和题目。变更记录注明这些影响位置及旧值、新值、变更依据。
5. 更新缺口清单，重新生成目录并运行审计。逐条复核变化的语义，不能只凭脚本通过就认定正确。

```bash
rg 'D2-001' knowledge/osmo360
python3 knowledge/osmo360/scripts/knowledge.py build
python3 knowledge/osmo360/scripts/knowledge.py audit --format json
python3 -m unittest discover -s knowledge/osmo360/tests -v
```

## 核验状态和冲突

- `verified`：在记录日期实际读取的官方来源支持这条带条件结论。
- `pending`：缺少足够依据。不得当成标准答案，检索在相关缺口中单独展示，不混入已核验答案。
- `conflict`：来源间或同页不同位置存在未解释的差异。登记双方原文位置和条件，不自行选择较好看的数值。

可以建立已核验的“某官方 FAQ 在指定条件下列出某值”这一窄结论，但必须在限制中显著说明其他官方位置的不同口径；不能将它提升为产品统一实测性能。涉及这种情况的题目考查如何识别差异，不要求记住单个争议值。

## 建议维护节奏

由团队指定一名资料维护负责人。建议每月人工复核一次；每次集中培训前检查固件、软件、兼容配件、价格和服务政策。发现新品或官方更正时，先复核已有比较对象，再决定下一版范围。

价格必须写明核验日期、币种、销售地区、渠道、套装及促销条件；不将不同地区或仅机身与套装的价格直接横比。本版按使用成本项目教学，未建立大陆实时报价表。

维护流程为人工触发，未建立定时任务。检查日志放在 [建设记录](BUILD.md)，未决事项放在 [缺口清单](GAPS.md)。

## 项目调用与心理指南的维护

[项目技能](../../.agents/skills/use-osmo360-knowledge/MODULE.md)负责将产品问答、人群心理和评论训练送到相应资料；[心理指南](../../.agents/skills/use-osmo360-knowledge/references/audience-guide.md)维护抽象需求假设。假设统一标记 `editorial_hypothesis / unvalidated`，不加入 `products/*.facts.jsonl`。历史人物、原句和审核记录继续放在原批次 `outputs/`；新稿另建本批人物与状态，不继承历史通过结论。

更新入口时同步检查项目 `AGENTS.md`、共用写手入口和本库索引的路径；保持已读入口不循环加载。验收应包含一个不依赖历史聊天的产品查询与一个心理／表达任务。技能结构检查、知识审计和训练稿检查各自只证明相应范围，均不能代替产品语义核验或用户表达认可。

## 卖点与价值的维护

卖点层维护在[selling-points.md](selling-points.md)，以`sp01`～`sp18`稳定锚点连接事实、场景和心理；`roles`与`upgrades`分别供角色选材和选用判断。保留七个字段及品类／本机／代际差异标记，用户价值属于编辑解释，不能新增为`verified`产品事实。参数仍以JSONL为维护源；更新事实卡后用`rg`查对应卡号，同步受影响卖点及升级表，避免只改参数表。

本轮读取情况分别记录在[一代卖点复核](sources/recheck-selling-first-2026-09-07.md)及[II代卖点复核](sources/recheck-selling-second-2026-09-07.md)。后续按实际读取范围更新日期，不因改写用户价值而刷新未读来源的核验日期。

## 详细场景与选材的维护

[场景总入口](scenario-bank.md)维护SC01～SC48，三份分册保留具体触发、任务差异、主辅SP、H假设、条件和不成立情形。更新事实时同时检索场景卡与[选材矩阵](training/scenario-to-copy.md)，若条件不能支持某个假想拍法，修改拍法或记录待核，不反向创造产品功能。单卡取用需携带其文件顶部的适用后期前提。

场景编号用于稳定引用，不因调整排序复用旧号。新增场景应有任务、观看者、操作或投入上的实质区别；同一卖点可以服务不同需求，不以地点／身份换名充数。后续产生真实原帖材料或消费者训练人物，分别按共享流程保存，不写回SC成为真实证据。维护范围与验证记入BUILD及evaluation，不建立后台自动更新。

## 体验材料与实际来源

按[体验材料指南](training/experience-materials.md)轻量收录，在[现有材料盘点](materials/STATUS.md)连接作品和证据原位置，不复制大媒体或另起参数库。原话、转写、编辑解释、假想稿与明确用户反馈分开；新到材料按实际看过／听过范围登记，作品存在不代表处理、音轨和完整讨论已读。使用阶段未知不推断，明确认可只更新对应原句与上下文，不把助手审稿变成用户认可。

真实实拍应记录设备、固件、光线、模式、机位、后期、导出和作者归属；不以不同条件的素材排名。编辑推演继续独立标注。

若以后读取抖音、小红书或 B站，先按项目要求调用 `read-social-links-with-social-helper`，一次性交入本次完整链接集合；本库只消费返回的证据，不新增采集规则。其他平台按项目原页读取规则执行。

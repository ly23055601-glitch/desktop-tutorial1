# Pocket主导表达、自然关联与产品证据（LH12）

先判断每条主评实际想说什么，按真实单锚点回应，提到产品时建立自然关联，见 [写作入口](../MODULE.md) 和 [七类风格案例](style-examples.md)。每帖先找成立的表达，再决定产出2–4条主评、每条配0–4条回复。自然点名与无名画面反应按话题混合，不预填数量、位置或“两条点名＋一条无名”。各条可以表达情绪、调侃、判断、偏好、疑问或真实个人需求，不固定类型组合，也不把全部主评套成“想拿Pocket拍”。产品能力仅在有证据且讨论需要时使用。LH12继续不设自动S2/S3配额；点名、心动、经历丰富程度也不自动提高产品证据等级。

## 每组主导表达与逐帖并排复核

每组用自由短句描述实际正文，不从固定枚举中选标签。是否点名从正文识别，不新增开关或评论类型：

- `dominant_expression`：这条评论主要在说什么，如“调侃猫抢走了开箱镜头”。不是七种风格的名称，也不是把同一个意思改写成几个类别名。
- `product_connection`：整组主评或回复出现产品名、产品能力或产品因果断言时必填，说明与主锚点如何相连，如“猫盯着正在拆封的Pocket盒子，回应抢镜关系”。整组仅聊具体画面的observed/S0可留空。只写“提到产品”“很相关”不算自然关联。

同帖实际交付的2–4条主评须并排比较实义是否不同；不同措辞、风格、`claim_mode`或`main_moves`不能代替这一判断。将实际说什么保存在各组 `dominant_expression`，逐帖复核只记录一次比较理由：

```json
{
  "qa": {
    "semantic_review": {
      "diversity_review": [
        {
          "id": "与allocation.id一致",
          "verdict": "passed",
          "comparison_reason": "第1组调侃猫抢镜，第2组担心杯子倒下，第3组希望构图停留更久；对象、主要态度和表达目的不同，已逐条对照正文。"
        }
      ]
    }
  }
}
```

`verdict`只在复核后填写`passed`或`revise`；模板空值表示待审。每个交付链接恰好一条记录，理由覆盖实际交付的全部组；2组是正常输出，无需为了三条扩写或填写减量理由。上面的三组记录仅演示字段，不规定组数。缺记录、理由为空、待审或`revise`均不可交付。检查器只核验记录映射、必要描述、明确重复与其他硬规则；描述字面不同不能证明正文实义不同，`passed`也不自动替代真人或模型并排审稿。

## 两种来源必须分开

原帖证据记录M/N/F/P，它只说明视频本身：

| 轴 | 分级 | 能证明什么 |
|---|---|---|
| M型号 | M0未知、M1作者声明、M2清晰机身/标签/UI确认 | 原片设备归属，M1须保留“作者说”的来源 |
| N需求 | N0无明确产品需求、N1可见拍摄阻力、N2作者明确提出或测试 | 原帖场景适配，不证明实际使用功能 |
| F功能 | F0未展示、F1作者声称、F2操作与结果连通、F3同条件对比 | 当前结果能否归因于某个功能 |
| P事实 | P0未核验、P1官方稳定事实、P2当日核验价格/固件/兼容等 | 参数和能力的可用范围，不反证视频用了该功能 |

`watermark_hint`只作线索，不进入型号、功能、需求或分级证据，默认不在评论中写水印。混拍须逐镜映射；漂亮成片、调色、构图和剪辑不替硬件获得能力证明。

个人材料单独放在引用该材料的组内：

```json
{
  "personal_context": {
    "source_ref": "user:materials#viewer-a",
    "facts": ["刚入手4p，十一去云南，担心不会设置"],
    "models": ["pocket_4p"]
  }
}
```

`source_ref`必须能回到实际用户材料并定位到具体说话者，例如同一文件内的`#viewer-a`，不能只填包含多个人的整份文件。`facts`保留支持正文的必要片段，`models`只列该来源确认的型号。不能给假经历编一个来源字符串后当成真实；人工验收必须打开对应材料核对。

个人素材只属于当前说话者；不把甲的已购情况与乙的行程拼在一起，不把一个人的经历分配给多个账号冒充不同消费者。本组个人型号不能给别的组授权，也不能回填原帖M/N/F；楼中楼的其他说话者不自动继承它。纯当下想法不需要假设个人背景，`personal_context`可省略或为null。

回复者首次使用自己的真实经历或型号时，在该组使用可选 `reply_personal_contexts`，如 `{"1":{"source_ref":"user:materials#reply-b","facts":["回复者已有p3，上一趟旅行素材尚未剪辑"],"models":["pocket_3"]}}`。键为实际回复序号字符串，值与主评个人材料结构相同且不能为null；默认空对象。

LH9及后续版本按`dialogue`中的说话者承接来源：A回来可继续使用本组主评的`personal_context`，B后续回来可继续使用B前面已绑定的材料。一个说话者绑定同一`source_ref`，同来源可以补充确实存在的facts/models；不同说话者不能共用这份个人来源。来源不跨组授权，旧LH8仍保持每条回复独立绑定的规则。无背景的当前念头不要求补来源，不能为了过检编材料。

## LH9及后续版本的对话关系

LH12对外使用编号主评与单层缩进回复，内部`dialogue`记录谁在回谁；不为了映射保留另一份带角色标签的正文。每组可有0–4条回复，零回复和单回复都可正常结束，不固定ABA、ABC或其他角色顺序。状态模板只有可复制的组结构示意，实际组数、回复数和说话者随内容填写。下面沿用原有假设搬家材料演示正文与内部映射，实际锚点须从最终草稿复制：

```text
1. Pocket3先不装箱了，周末搬家也想拍这个转场
    - 搬空以后还会多录一会儿吗
    - 会，空房子也想留一段
```

```json
{
  "main_speaker": "A",
  "replies": [
    {"reply": 1, "speaker": "B", "reply_to": "main", "anchor_quote": "周末搬家", "response_move": "询问是否也记录搬空后"},
    {"reply": 2, "speaker": "A", "reply_to": "reply:1", "anchor_quote": "还会多录一会儿吗", "response_move": "回答会并说明想留下什么"}
  ]
}
```

- `main_speaker`固定A，回复`speaker`可为A/B/C/D/E；这些是文案关系标记，不是账户或博主身份
- `reply`为实际回复序号，每条正文恰好映射一次；`reply_to`为同组`main`或较早的`reply:n`，不指向自己说的父句、未来回复或不存在的回复
- 第一条回复指向主评；LH12后续回复按实际父句映射，不强制存在回复接回复，也不为满足结构续写第二条。多条回复是否真正接话、是否只是平行旁白，由语义审稿判断
- `anchor_quote`引用被回复正文的真实连续片段；`response_move`用非空描述写明如何回应，不限定话术或强制问答
- LH12最终稿不展示A/B标签，缩进回复按出现顺序映射内部`reply`序号；若输入保留旧式标签，标签中的发言者、接收者仍须与状态一致
- 零回复组可省略`dialogue`或保留空`replies`数组，`reply_personal_contexts`为空，不残留旧回复的映射或来源。实际有回复时不能省略内部映射；单回复无需补成对话链
- LH9–LH11历史状态仍按原版本执行角色标签和至少一条回复接回复的要求，不用LH12宽松数量规则回写旧批次

字面引用匹配只能定位父句，不能证明回应自然。还须按 [互动对话验收](reply-dialogue.md) 判断是否答到问题、接住调侃或情绪，以及下一句有没有实际回应。新添的过去经历是否得到facts支持，也必须人工核对，不能靠相同`source_ref`放行。

## 贴帖互动：observed/S0

有真实单锚点，只是情绪、调侃、偏好或看法时，可复用`claim_mode=observed`、`target_s_level=S0`、`actual_s_level=S0`。锚点留在内部证据记录，正文可以省略已经由原帖提供的背景，不必每条先复述画面；短反应成立时说完就停，也可整组零回复。是否空泛须结合原帖判断，不能仅因句子短就补细节或产品名。`claim_id`留空，`benefit_basis`为visual或workflow；点名本身不升级S级。即使原帖N0/F0，其他门禁与并排复核均通过的组仍可交付，无需硬补个人需求、强种草组或登记证据停止。

LH11及后续版本中整组无产品名、无产品能力或因果断言的纯画面互动用`benefit_basis=visual`，`product_connection`可留空；出现产品名或上述断言则仍必填。有效observed/S0组可免于`W_SEED_ZERO_PROXY`产品收益提示；缺锚点、缺复核、待改或有硬件断言的组不获豁免，非纯画面组也不能缺产品关联。只对实际点名的主评检查称呼变化，主评与回复仍不用Osmo。不因为写了`observed`就跳过产品事实核验：主评和每条回复都接受与personal_need相同的能力断言与当前画面因果检查，换模式或把断言塞到回复里无效。

LH10及后续版本的事实核验按逐句实际断言触发，不以`claim_mode`或低S级绕过：声称能力就须绑定真实注册claim、匹配型号与官方P证据，当前画面因果还须通过对应M/F及操作结果链；有据的低S事实保持原级，无需补收益，无断言的自然互动也无需claim。

LH11及后续版本不依赖主评点名来发现回复事实：“这台支持4K”“这么稳全靠这台相机”等仍按实际断言检查；设备不明时核实或删去断言，不能用同帖另一组的名称、个人材料或claim自动补证。纯画面感受和真正的疑问不当作能力断言，人物或动物的“它”也不自动继承设备身份。无名主评不意味着整组可以免检。

## 真实个人需求：personal_need

视频讲的设置正好用于已确认的出行计划、搬家纸箱转场让人想到记录空房、练舞对比让人想留住第一天，都可以成为完整的一条评论，无需追加卖点、问句或购买结论。

```json
{
  "main_anchor_ids": ["settings-explained"],
  "dominant_expression": "出行前担心不会设置，看到讲解后放心了",
  "product_connection": "Pocket设置讲解回应个人材料中的出行使用顾虑",
  "main_moves": ["need", "reaction"],
  "seed_layers": {"main": ["need", "product"], "replies": []},
  "light_meme_anchor": "",
  "claim_mode": "personal_need",
  "claim_id": "",
  "target_model": "pocket_4p",
  "contrast_models": [],
  "benefit_basis": "workflow",
  "user_benefit": "",
  "usage_condition": "",
  "boundary": "",
  "need_connection": "视频解释出发前需要的设置，回应个人材料中不会用的顾虑",
  "evidence_sources": [],
  "target_s_level": "S1",
  "actual_s_level": "S1"
}
```

以上字段应与状态模板的其他必要字段合并。使用已购等亲历时还须填写前面的 `personal_context`。`need_connection`解释真实连接，不能只写“有需求、很相关”；它是审稿信息，不进入纯净评论。

- `personal_need`用于LH8及后续版本，最高S1，`claim_id`为空，`benefit_basis`为workflow或visual。LH10及后续版本仍额外需要`need_connection`，不以`product_connection`替换。原帖N0/F0也可成立，不抬高 `scenario_fit_cap` 或原片因果上限。
- S1可以是明确的使用需求、被帮助的反应、记录念头或真实购前问题，不要求必须提问。它不表示评论质量低。
- “刚买＋要出门＋怕不会＋教程来得正好”围绕一个主要表达任务，不按每段背景拆成多个营销动作。`main_moves`仍记1–2个主要动作，如need/reaction；`seed_layers`不把心理放松误填为硬件benefit。
- 有个人材料确认某型号时，正文可以说本人准备如何用它，不能写成“博主这段就是该型号拍的”。单纯未知原帖设备不否定本人已确认设备。
- 没有任何自然连接时停止植入，不以“所有生活都可以拍”为由硬接产品。只有教程罗列参数、没有操作解释时，不写成看完已经学会操作。
- 需要楼中楼时自然承接，不借回复补造经历、硬件结论或博主答案。若组内确实加入产品能力判断，整组改用下面对应的证据路线，不能用personal_need逃过事实核验。

## 产品能力路线与S级

| S级 | 含义 | 约束 |
|---|---|---|
| S0 | 贴帖内容互动 | 名称本身不加级 |
| S1 | 需求被触发、使用念头、被帮助或具体疑问 | 不代表硬件收益已经证实 |
| S2 | 已核验卖点转为明确产品收益 | 注册claim、正确型号、足够P与适用条件 |
| S3 | 型号差异结合使用条件形成选择 | 不能仅凭共享能力、心动或购买词升级 |

除personal_need外，模式继续为：

- `observed`：描述可见内容，不做产品因果
- `attributed`：保留作者声明的来源，不冒充直接演示
- `scenario_fit`：N1/N2与官方P证据成立时讨论未来适用情况，不反推原片设备或效果
- `causal`：只有M2＋F2/F3＋P且操作与结果连通，才说明功能促成当前结果
- `comparative`：同条件对比至少F3；仅凭官方结构与需求做未来选择时用scenario_fit

每组最多一个 `claim_id` 和一个核心硬件收益。只有一个已核验claim的共享能力可支撑品类S2，不能直接说某代比另一代更值得买。`benefit_basis=workflow/visual`不能冒充产品S2/S3。

需要写参数或能力时读取 [产品知识](product-knowledge.md) 并以当前官方页面复核，再按 [事实注册表](product-claims.json) 绑定已核验claim。注册表与历史知识快照不是当前事实自动成立的证明。慢动作、变焦、动态范围、续航、防水及麦克风兼容必须带适用条件；价格、固件、库存等必须当日核验。

不要为了分级把评论变成理性评测或向博主要证据。准确性仍是底线，有效的个人需求评论无需硬件论证也可以交付。

## 状态契约与兼容

- 新批次 `rule_version=2026-09-05-LH12`，`claim_registry_version=2026-09-02-LH5`，不改历史LH5–LH11。模板只保留一个可复制的组结构，`claim_mode`和目标/实际S级留空待判定，`dialogue.replies`为空；这不表示实际只写一组，也不预填personal_need或S1。
- 顶层 `delivery_mode`为with_replies或main_only；LH12每帖2–4组，with_replies允许每组0–4条回复，main_only各组均为0。`groups`只映射实际输出，2组无需`reduced_output_reason`，不为填满模板拆分同一个意思。
- 保留每帖M/N/F/P、原片因果和场景适配上限。`strong_seed_group`默认为null，不因N/F存在强制一组S2/S3；显式指定后必须指向成立的强组。
- 普通内容虽无硬件证据，但真实personal_need或上述已复核的observed/S0成立时，无需登记为 `evidence_stop_ids` 或填写未达目标理由。整组无名的纯画面互动仍可交付；完全没有合理贴帖话题时在状态与交付说明中记录停止，不伪造评论块。
- 每组 `main_anchor_ids`恰好一个，`main_moves`为1–2项，`seed_layers.main`最多两层。每组记录`dominant_expression`，按整组正文是否涉及产品填写`product_connection`；`need_connection`在personal_need时保留，与可选`personal_context`只补充需求关联和来源，不替换原帖证据。不同证据模式可同帖混用，不设置固定分配。
- 点名随表达安排，不固定“两条点名＋一条无名”，也不为四条主评凑第四个名称。同帖实际点名的名称有变化且指向同一目标型号；未知代际用Pocket、大疆Pocket、DJIPocket。无名组不在回复里补全称完成任务，评论和回复禁Osmo，来源仍可保留官方名称。
- 对外交付与检查共用同一份最终编号稿：每帖主评从`1.`连续编号，回复用单层缩进项目符号，按出现顺序与`dialogue`一一映射。编号的句点不属于正文，主评和回复正文仍不用句号。第四组与前面各组执行相同的锚点、个人来源、产品事实和语义检查。

原有证据契约仍保留：

```text
causal/comparative: kind:shared_anchor:detail
混拍映射: shot:anchor:model:source
```

因果至少一项操作/UI与一项结果共用anchor；comparative另需同条件/比较来源。裸写operation/result或不同anchor不能形成证据链。混拍单写mapped不够，需逐镜 `shot_mapping_evidence`。

`actual_s_level`必须显式填写；S2/S3的 `user_benefit`引用正文实际收益，S3的 `usage_condition`和 `boundary`引用正文且对应claim所需边界。`source_urls`必须匹配该claim登记的官方页，查询参数可不同。对比正文有多个型号时须明确各自角色，涉及能力时保留登记的比较对象与条件，不能借共享claim放大型号优势。

## 检查与判定

```bash
python3 scripts/check_comment_homogeneity.py draft.md --state pocket_comment_state.json --product-policy off --seeding-policy strict
```

沿用`--product-policy off`；LH7及后续状态本已忽略旧产品比例开关。不要把本轮写作偏好实现为旧版硬性两明一隐及隐性组回复补名要求。

不例行加全局 `--strict`，它会把启发式语气警告也当失败。机器检查主要验证声明结构、已登记的证据边界、名称、格式与近重复；真实性、语境连接、自然情绪仍按入口的验收清单逐条对照原材料。

验收的关键区别：

- 正：个人材料确认已买4p并将去云南，设置教学让他放心，S1可交付
- 错：用同一份个人材料推断博主视频也由4p拍摄
- 正：纸箱转场让发布者想到记录自己的搬家，产品只承担记录工具角色

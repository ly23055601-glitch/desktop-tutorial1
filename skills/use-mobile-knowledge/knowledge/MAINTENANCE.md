# Mobile 知识库维护

## 哪份文件负责什么

- `products/*.facts.jsonl` 与 `compatibility/*.jsonl` 维护产品结论；字段约定见 [SCHEMA](SCHEMA.md)。型号目录为 `products/models.jsonl`。
- `sources/*.jsonl` 登记实际读过的官方来源；原件与提取快照保存在 `sources/`，用 SHA256 绑定本次读取内容。下载列表不代表已经读过其列出的 PDF。
- `scenarios/cards.jsonl` 仅关联既有产品依据。FAQ、场景阅读版和代际差异表解释已有事实，不能成为新参数的独立来源。
- `use_cases/cards.jsonl` 在概览场景下细化具体任务与培训选材，关联卖点、角色、事实和兼容记录；详细阅读页和卖点反查表由脚本生成，不能独立维护参数。
- `scripts/maintain.py render` 从结构化记录重建逐条阅读版、来源目录、主题覆盖和缺口清单；`audit` 检查结构及引用。索引导读、FAQ和差异表中的人工解释仍需随事实变更复核。

## 何时更新

写作引用、用户提出事实疑问、官方发布新固件／兼容表／套装或资料出现冲突时，人工核对相关来源。价格、套装、软件和兼容性按实际使用当日确认，稳定硬件事实进入评论正文前也核对当前官方依据。没有后台定时任务，旧核验日期不自动变成今天。

## 更新步骤

1. 打开对应型号的官方规格、FAQ、支持页、手册、兼容列表或中国区商城，读完整条款、对应型号列与脚注。中国区 URL 若跳到英文页，按实际响应标记语言和地区，不套用中国区价格或套装。
2. 保存带新日期或版本的原件／快照，核对正文可读并计算 SHA256。新来源使用新 ID；需要保留同一来源 ID 时，将旧路径、日期和哈希写入 [变更记录](CHANGELOG.md)，不能覆盖旧文件丢失依据。
3. 同一结论修正保留事实 ID，独立新能力新增 ID。记录设备组合、App／系统／固件范围和使用条件。官方页未给最低固件时保持未明，不从发布日期推算。
4. 未解决的资料差异设为 `conflict`，缺依据设为 `pending`，填写 `gap_reason`。保留双方定位，不能通过选择有利来源消除冲突；没有列出不等于明确不支持。
5. 更新关联场景、FAQ、差异表和型号目录；已核变未核后，移除场景中的肯定能力依据。重新生成阅读版和缺口清单，再运行审计和受影响的工作问题。

从本知识库目录运行，或使用脚本绝对路径（脚本以自身位置定位资料，不依赖工作目录）：

```sh
python3 scripts/maintain.py render
python3 scripts/maintain.py audit
```

审计只证明记录结构、引用和保存证据一致，不能证明语义正确或官网此刻仍可访问。验收记录应写实际执行日期、结果与遗留缺口，不以旧通过记录为新版本背书。

## 写作边界

`experience_materials/`单独保存真实表达的读取范围、短摘录、讨论上下文、未决关系及拍法分析；`records.jsonl`登记来源、观察记录哈希和证据覆盖。观察摘要不冒充网页原件，公开自述不写进产品事实。更新时核对原来源及实际父句，不能把未读作品、未知手机／App／配件或未获用户认可的原句标成完整材料。入口见[体验材料指南](experience_materials/guide.md)。

写法与用户表达反馈继续维护在共用写手能力库。本库提供型号事实、组件关系、适配、场景解释和独立的角色心理假设。训练人物经历留在当批训练状态中；真实帖子证据需另行读取，不能用本库推定原帖设备或启用模式。未来若采集抖音、小红书、B站，仍一次交入完整链接集合并遵循统一社媒读取技能。

## 跨项目维护

唯一维护源为个人技能 `use-mobile-knowledge/knowledge/`；op 的 `knowledge/mobile` 是链接，同一次修改会被各项目读取。复制到其他机器时保留整个技能目录及原件，不把 op 路径作为依赖。产品问答与人群分析可独立使用，评论训练还需共享 `write-consumer-comments`，明确真实资料审查时另需原 Mobile 评论入口。

`audiences/profiles.jsonl` 单独保存编辑假设，格式见 [人群记录格式](audiences/SCHEMA.md)。修改角色时同步更新阅读指南；不改变产品事实状态或核验日期。事实更新也要检查角色引用的型号与条件；自然表达示例维持 training_fiction 和 pending_calibration，只有用户明确认可才单独记录其认可范围。新增真实研究应另存研究材料及来源，不把编辑假设升级为调研结论。

## 卖点同步

卖点维护源为 `selling_points/cards.jsonl`，只存能力概括、用途、价值与引用，不复制参数条件。产品事实更新后检查相关卖点是否仍成立，重新render生成按型号阅读页，并由audit检查型号、角色、引用与状态。具体价值仍需人工复核，不因结构检查通过变成用户研究。

同一官方URL重新获取后若原件SHA256完全一致，可复用已有原件和提取快照，另记重取日期与实际复读范围；不能因此整体刷新未复读事实的日期。本轮记录见 [卖点补充验收](evaluation/selling-points/acceptance.md)。历史版本清单只代表当时文件，后续新增的验收与清单各自保存。

## 详细场景与选材同步

修改产品事实或卖点时，用 `rg -n '事实编号|卖点编号' use_cases/cards.jsonl` 找到受影响的详细场景，检查拍摄步骤、条件摘要、价值解释及不可推论。场景编辑日期独立保存；心理和价值仍为假设，选材仍为待校准的 `training_fiction`。

总 `render/audit` 已包含详细场景。可独立执行 `python3 scripts/use_cases.py audit`，或用其 `query` 子命令按场景编号、型号、关键词、卖点编号取完整依据。查询把卡片和卖点的引用一并展开，同时保留型号缺口；状态变化后不能继续用旧场景作肯定答案。

场景来源是编辑构思，官方来源只支持相关能力；不能将两者的检查合并成“用户场景已经验证”。新增真实案例需另外保存原始来源与范围，不用构思细节补真实帖子的背景。
